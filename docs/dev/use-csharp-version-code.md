# Debugging Game Code with UseCSharpVersionCode

:::info

This page is for development and debugging. `UseCSharpVersionCode` makes the game execute the C# pseudocode generated from its Hashlink bytecode instead of the native bytecode, so you can set breakpoints and step through the game's internal logic in a .NET debugger such as Visual Studio.

:::

## How It Works

Dead Cells game logic runs on the Hashlink virtual machine. The `GameProxy` assembly generated by DCCM contains C# proxy types for the game's Haxe classes. By default these proxy methods only forward calls to the native Hashlink functions, so a breakpoint placed inside them is never hit during normal gameplay.

When `GeneratePseudocodeAssembly` is enabled, DCCM also compiles the game's Hashlink bytecode into C# method bodies. `HaxeProxyUtils.UseCSharpVersionCode` then switches the target Hashlink function's entry point to that C# implementation. From then on the game runs the C# version of the function, allowing the debugger to stop inside it and inspect the call flow, arguments, locals, and so on.

This is a debugging aid. Keep it in a development build rather than a normal gameplay mod.

:::warning

`UseCSharpVersionCode` is still experimental and not yet stable. The generated pseudocode may not exactly match the native Hashlink semantics, so some functions may misbehave, return incorrect results, or crash when baked. Use it only for debugging and code inspection in a development environment.

:::

## Prerequisites

1. Enable pseudocode generation in `coremod/config/modcore.json`:

   ```json
   {
     "GeneratePseudocodeAssembly": true
   }
   ```

   Restart the game after changing it. DCCM regenerates `GameProxy` with pseudocode; the first launch may take longer. When pseudocode is enabled, DCCM also writes a copy to `coremod/cache/GamePseudocode.dll` for decompilers/viewers, while the runtime keeps using `coremod/cache/GameProxy.dll`.

2. Keep the option enabled while calling `UseCSharpVersionCode`. The API throws `InvalidOperationException` if the loaded proxy was generated without pseudocode.

3. Reference `HaxeProxy` (included by MDK by default) and import `HaxeProxy.Runtime`.

## API

```csharp
public static void UseCSharpVersionCode(Type t, bool throwOnCompiled)
public static void UseCSharpVersionCode(MethodInfo m, bool throwOnCompiled)
```

| Overload | Behavior |
| --- | --- |
| `Type` | Iterates the type's public instance/static methods. Only methods with `[HashlinkFIndex]` are baked; methods marked `[HashlinkShouldUseNative]` are skipped. |
| `MethodInfo` | Bakes one method. Throws if the method has `[HashlinkShouldUseNative]` or no `[HashlinkFIndex]`. |

`throwOnCompiled` controls what happens when the target Hashlink function is already compiled to .NET (for example, baked by another type or mod):

- `false` — skip it silently. Use this for a batch bake helper.
- `true` — throw `InvalidOperationException`.

:::warning

- Only methods generated into `GameProxy` from the game's Haxe bytecode carry `[HashlinkFIndex]`. Calling the API on your own C# types has no effect.
- `[HashlinkShouldUseNative]` marks functions whose decompiled IL cannot faithfully reproduce the native Hashlink semantics. Do not try to force-bake them.
- The feature is not yet stable. Even functions without that attribute may behave differently from the native implementation; cross-check any suspicious behavior with a decompiler/disassembler.
- Baking is process-wide: once a function is switched to the C# version, all callers use it. It cannot be undone at runtime.

:::

## Example

The following helper bakes a set of core boot/UI types. Call it as early as possible. In a regular mod, `Initialize()` runs during `IOnBeforeGameInit`, before the original Haxe `Boot.main` body continues, which is early enough for the game logic that follows.

```csharp
using System;
using System.Collections.Generic;
using dc;
using HaxeProxy.Runtime;
using ModCore.Mods;

namespace DebugHelper
{
    public class DebugHelperMod(ModInfo info) : ModBase(info)
    {
        public override void Initialize()
        {
            BakeCode();
        }

        private void BakeCode()
        {
            List<Type> types =
            [
                typeof(_Boot),
                typeof(Boot),
                typeof(dc.hxd.App),
                typeof(dc.hxd._App),
                typeof(Main),
                typeof(_Main),
                typeof(dc.pr.TitleScreen),
                typeof(dc.pr._TitleScreen),
                typeof(dc.hxd.fmt.pak.FileSystem),
                typeof(dc.hxd.fmt.pak._FileSystem),
                typeof(_Sys),
                typeof(Sys),
                typeof(dc.libs.Process),
                typeof(dc.libs._Process),
                // typeof(Assets),
                // typeof(_Assets),
                typeof(AssetsLibManager),
                typeof(_AssetsLibManager),
                typeof(dc.haxe.MainLoop),
                typeof(dc.haxe._MainLoop),
                typeof(dc.hxd._System),
                typeof(dc.hxd.System),
                typeof(dc.haxe._EntryPoint),
                typeof(dc.hxd.res.BitmapFont),
                typeof(dc.hxd.res._BitmapFont),
            ];

            Logger.Information("Cook types: {num}", types.Count);

            foreach (var t in types)
            {
                HaxeProxyUtils.UseCSharpVersionCode(t, false);
            }

            Logger.Information("Cook types finished!");
        }
    }
}
```

:::tip

The names above are game-proxy types, so add the matching `using` directives or fully qualify them. For example, `App` is `dc.hxd.App`, not `dc.App`.

:::

## Debugging Tips

- Attach your debugger to the game process.
- In Visual Studio, disable **Just My Code** (`Tools > Options > Debugging > General`) so you can step into generated/framework code.
- Consider enabling **Suppress JIT optimization on module load** for more accurate stepping.
- Set breakpoints in the baked `GameProxy` methods. To understand the code before setting breakpoints, decompile `coremod/cache/GamePseudocode.dll` (see [Viewing Game Code](./look-persudo.md)).
- If a method is skipped because of `[HashlinkShouldUseNative]`, its native implementation still runs; use crashlink/hlbc to inspect it.

## FAQ

**`InvalidOperationException` from `UseCSharpVersionCode`?**

Enable `GeneratePseudocodeAssembly` in `coremod/config/modcore.json` and restart. The API requires a pseudocode-enabled proxy.

**The breakpoint is still not hit?**

Make sure the type/method was actually baked. A type bake only covers public methods with `[HashlinkFIndex]`; constructors and `[HashlinkShouldUseNative]` methods are not included. Also check whether the function was already compiled elsewhere — `throwOnCompiled: false` skips it silently.

**Does this affect players?**

Yes, it is process-wide. Use it only for debugging/development and remove it from production builds unless you intentionally want the game to run the C# version.
